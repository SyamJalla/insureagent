This code builds an **AI-powered insurance customer-support agent** using:

* **LangGraph** → orchestrates multiple specialized agents
* **OpenAI** → makes routing and response decisions
* **ChromaDB** → semantic search over insurance FAQs
* **SQLite** → stores/query customer, policy, billing, payment, and claim data
* **Langfuse + OpenTelemetry** → tracing/observability
* **Hugging Face Datasets** → provides the insurance FAQ dataset
* **YAML prompts** → keeps agent instructions outside the Python code

At a high level:

```text
User question
     │
     ▼
Supervisor Agent
     │
     ├── Policy Agent ──────► SQLite
     │
     ├── Claims Agent ──────► SQLite
     │
     ├── Billing Agent ─────► SQLite
     │
     ├── General Help ──────► ChromaDB ──► FAQ
     │
     └── Human Escalation
             │
             ▼
      Final Answer Agent
             │
             ▼
           User
```

## 1. FAQ / RAG setup

The first section creates a knowledge base from Hugging Face.

```python
ds = load_dataset("deccan-ai/insuranceQA-v2")
```

It loads the insurance question-answer dataset.

Then:

```python
df = pd.concat([split.to_pandas() for split in ds.values()])
```

combines all dataset splits into one Pandas DataFrame.

This:

```python
df["combined"] = "Question: " + df["input"] + " \n Answer:  " + df["output"]
```

creates a document containing both the question and answer.

Finally:

```python
df.to_csv("insurance_faq.csv", index=False)
```

saves the dataset locally.

### ChromaDB

```python
chroma_client = chromadb.PersistentClient(path=persist_directory)
```

creates a persistent vector database.

Then:

```python
collection = chroma_client.get_or_create_collection(
    name=collection_name
)
```

creates/opens the FAQ collection.

`add_data_to_collection()` puts FAQ documents into ChromaDB.

```python
collection.add(
    documents=batch_df["combined"].tolist(),
    metadatas=[{"question": q, "answer": a} ...],
    ids=...
)
```

ChromaDB can then perform semantic search:

```python
results = collection.query(
    query_texts=[query],
    n_results=3
)
```

So if the user asks:

> What does life insurance cover?

the system retrieves the three most semantically relevant FAQ entries.

This is essentially a **RAG (Retrieval-Augmented Generation)** component.

# 4. Database tools

The next group of functions acts as **tools that the AI agents can call**.

For example:

```python
get_policy_details(logger, policy_number)
```

looks up a policy.

It executes:

```sql
SELECT p.*, c.first_name, c.last_name
FROM policies p
JOIN customers c
    ON p.customer_id = c.customer_id
WHERE p.policy_number = ?
```

The `?` is important because the policy number is passed as a SQL parameter rather than concatenated into the query.

# 6. Tool calling

One of the most important pieces is:

```python

```

It allows an LLM to decide whether it needs a tool.

For example, the claims agent might receive:

> What's the status of claim CLM000123?

The model can decide to call:

```text

```

Your Python code then executes the actual function:


and sends the result back to the model.

Conceptually:

```text
User

 ▼

 │

 ▼

 │
 ▼
SQLite
 │
 ▼
claim information
 │
 ▼
LLM
 │
 ▼
natural-language answer
```

That's a classic **LLM tool-calling architecture**.

This is where everything is connected:

```python
workflow = StateGraph(GraphState)
```

You register nodes:

```python
workflow.add_node("supervisor_agent", supervisor)
workflow.add_node("billing_agent", billing)
workflow.add_node("policy_agent", policy)
workflow.add_node("claims_agent", claims)
workflow.add_node("general_help_agent", general)
workflow.add_node("final_answer_agent", final_agent)
workflow.add_node("human_escalation_agent", human)
```

Think of each node as a worker.

Then:

```python
workflow.set_entry_point("supervisor_agent")
```

means every conversation begins with the supervisor.

# 13. Conditional routing

This is the key routing logic:

```python
workflow.add_conditional_edges(
    "supervisor_agent",
    decide_next_agent,
    {
        "policy_agent": "policy_agent",
        "billing_agent": "billing_agent",
        "claims_agent": "claims_agent",
        "general_help_agent": "general_help_agent",
        "human_escalation_agent": "human_escalation_agent",
        "end": "final_answer_agent"
    }
)
```

So:

```text
Supervisor
   │
   ├── policy_agent
   ├── billing_agent
   ├── claims_agent
   ├── general_help_agent
   └── human_escalation_agent
```

After a specialist finishes:

```python
workflow.add_edge("billing_agent", "supervisor_agent")
workflow.add_edge("policy_agent", "supervisor_agent")
workflow.add_edge("claims_agent", "supervisor_agent")
workflow.add_edge("general_help_agent", "supervisor_agent")
```

it goes **back to the supervisor**.

Therefore the architecture is actually:

```text
                 ┌───────────────┐
                 │   Supervisor  │
                 └───────┬───────┘
                         │
          ┌──────────────┼───────────────┐
          ▼              ▼               ▼
       Policy          Claims          Billing
          │              │               │
          └──────────────┼───────────────┘
                         ▼
                    Supervisor
                         │
                         ▼
                 Final Answer
```

This allows the supervisor to decide whether another step is needed.

# 14. Iteration limit

You have:

```python
n_iter = state.get("n_iteration", 0) + 1
```

and:

```python
if n_iter >= 3:
```

So the supervisor cannot keep looping indefinitely.

After three iterations it does:

```python
"next_agent": "human_escalation_agent"
```

This is essentially a **circuit breaker**.

Without this, a badly designed routing system could potentially do:

```text
Supervisor
 → Billing
 → Supervisor
 → Billing
 → Supervisor
 → Billing
 → ...
```

forever.

# 15. Final answer agent

Once the workflow decides that the task is finished:

```python
"end": "final_answer_agent"
```

the final answer agent runs.

It takes the specialist response:

```python
specialist_response
```

and asks another LLM to turn it into a clean customer-facing response.

So the specialist might produce something somewhat technical:

```text
Billing lookup returned:
status=pending
amount_due=327.42
```

and the final agent could turn that into:

> Your latest bill is currently pending, with an amount due of $327.42.

This gives you a separation between:

```text
Data retrieval
      ↓
Specialist reasoning
      ↓
Customer-facing response
```



You also explicitly call:

```python

```

at the end of a query.

---

### OpenTelemetry

You also use:

```python
tracer = trace.get_tracer(__name__)
```

and:

```python
with tracer.start_as_current_span("sqlite_get_claim_status"):
```

This creates spans for database operations.

You record attributes such as:

```python
span.set_attribute("db.system", "sqlite")
span.set_attribute("db.operation", "SELECT")
span.set_attribute("claim_id", claim_id)
```

So your observability tree could look conceptually like:

```text
insurance_query
│
├── supervisor_agent
│
├── claims_agent
│   └── run_llm
│       └── sqlite_get_claim_status
│
└── final_answer_agent
```

That's useful for debugging latency, failures, routing behavior, and tool usage.

# 19. Example end-to-end execution

Suppose the user asks:

> What is the status of claim CLM000015?

The flow would roughly be:

### Step 1 — Initial state

```text
user_input =
"What is the status of claim CLM000015?"
```

### Step 2 — Supervisor

LLM determines:

```json
{
  "next_agent": "claims_agent",
  "task": "Retrieve the status of claim CLM000015"
}
```

### Step 3 — Claims agent

The claims agent gets the task and calls:

```python
get_claim_status(
    logger,
    claim_id="CLM000015"
)
```

### Step 4 — SQLite

SQL retrieves:

```text
claim_id
policy_number
claim_date
incident_type
estimated_loss
status
policy_type
```

### Step 5 — Claims LLM

The tool output is sent back to the LLM.

It produces something like:

```text
The claim is currently under review.
```

### Step 6 — Supervisor

The specialist response goes back to the supervisor.

The supervisor determines that the request is complete.

### Step 7 — Final answer agent

The final agent creates a polished response.

### Step 8

Graph terminates:

```text
final_answer_agent → END
```

# 21. Important bugs/issues in the current code

There are several things I'd fix before treating this as production-ready.

### 1. `get_policy_details()` has a real bug

You do:

```python
result = cursor.fetchone()
response = dict(zip(columns, result))
```

**before `columns` is defined**.

`columns` is only created later:

```python
columns = [
    desc[0]
    for desc in cursor.description
]
```

So if a policy is found, this can raise:

```text
UnboundLocalError: local variable 'columns' referenced before assignment
```

Move the `columns` creation before `response`.

---

### 2. `GraphState` doesn't declare some fields you use

You use:

```python
needs_clarification
clarification_question
user_clarification
```

but they aren't declared in `GraphState`.

Add them if you're using them as formal graph state.

---

### 3. Initial state doesn't contain `policy_number` or `customer_id`

Your specialist agents expect them, but the initial state doesn't explicitly initialize:

```python
policy_number
customer_id
```

You should initialize them, for example:

```python
"policy_number": None,
"customer_id": None,
```

---

### 4. `messages` handling is potentially confusing

You're using:

```python
Annotated[List[Any], add_messages]
```

but some nodes return:

```python
[("assistant", result)]
```

while `final_answer_agent` manually replaces:

```python
state["messages"] = clean_messages
```

It's better to establish one consistent message/state strategy.

---

### 5. The supervisor doesn't actually use the latest specialist result very clearly

The specialist nodes return messages, but the supervisor's prompt is primarily based on:

```python
conversation_history
```

You should make sure the specialist response is reliably incorporated into the state that the supervisor sees.

---

### 6. `ask_user()` blocks the application

This:

```python
answer = input(...)
```

works for a notebook/terminal application, but it won't work properly in a typical web API, Streamlit app, chatbot backend, etc.

For production, clarification should normally be represented as a graph state such as:

```text
needs_clarification = True
clarification_question = "What is your policy number?"
```

Then the application sends that question to the user and resumes the graph when the user responds.

---

### 7. Your supervisor iteration limit is quite aggressive

```python
if n_iter >= 3:
```

means the system escalates after only three supervisor visits.

Since the normal architecture is:

```text
Supervisor → Specialist → Supervisor
```

you can reach the limit relatively quickly.

---

### 8. Tool schemas should mark required arguments

For example:

```python
"parameters": {
    "type": "object",
    "properties": {
        "policy_number": {"type": "string"}
    }
}
```

but there is no:

```python
"required": ["policy_number"]
```

The model therefore has less guidance about which parameters are mandatory.

---

### 9. Hard-coded database path

Your database functions use:

```python
"datasources/database/insurance_support.db"
```

instead of accepting the DB path.

That makes testing and deployment harder.

A configuration value would be cleaner.

---

### 10. There are duplicated imports

For example:

```python
from datetime import datetime, timedelta
```

and later:

```python
from datetime import datetime
```

Also:

```python
from functools import wraps
```

is imported twice.

Not harmful, but unnecessary.

# 22. What this project really is

If I had to describe your code in one sentence:

> **It is a LangGraph-based multi-agent insurance support system where an LLM supervisor routes customer questions to specialized policy, claims, billing, or FAQ/RAG agents, which use SQLite or ChromaDB tools to retrieve information, with Langfuse/OpenTelemetry providing observability.**

The important conceptual separation is:

**LangGraph = orchestration**

**OpenAI = reasoning / tool selection / response generation**

**SQLite = structured transactional data**

**ChromaDB = unstructured knowledge / FAQ retrieval**

**YAML = agent instructions**

**Langfuse + OpenTelemetry = observability**

**Python functions = tools**

That separation is the core design of your application.

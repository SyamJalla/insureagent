# 4. API Layer

You have:

text
Amazon API Gateway
        ↓
Supervisor


Good.

But I would introduce a *Conversation/Agent API service* between API Gateway and the agent runtime.

text
API Gateway
     ↓
Conversation Service
     ↓
Agent Runtime
     ↓
Supervisor


Why?

Because the API layer should handle things like:

* request validation
* conversation ID
* customer ID
* authentication context
* rate limiting
* idempotency
* request correlation ID
* session management
* streaming responses
* throttling

The Supervisor shouldn't have to deal with those concerns.

# 5. Supervisor Agent

This is the *most important component* in your architecture.

Currently:

text
Insurance AI Orchestrator
(Supervisor Agent)


This is correct conceptually.

But I would make its responsibilities very explicit.

### Supervisor should do

text
User request
     ↓
Intent detection
     ↓
Entity extraction
     ↓
Determine required agents
     ↓
Plan
     ↓
Execute agents
     ↓
Validate results
     ↓
Determine escalation
     ↓
Final response


For example:

> "My claim is delayed and I was charged twice this month."

Supervisor:

text
                    Supervisor
                    /        \
                   /          \
                  ↓            ↓
            Claims Agent   Billing Agent
                  │            │
                  ↓            ↓
             Claim API     Billing API
                  │            │
                  └─────┬──────┘
                        ↓
                  Result Validator
                        ↓
                  Final Response


### Important improvement

Don't make the supervisor directly query every enterprise system.

Instead:

text
Supervisor
    ↓
Specialized Agent
    ↓
Domain Tools
    ↓
Enterprise System


This provides much better separation of responsibility.

## Policy Agent

The Policy Agent should own *policy-related reasoning*.

text
Policy Agent
     │
     ├── get_policy
     ├── get_coverage
     ├── get_policy_status
     ├── get_documents
     ├── calculate_eligibility
     └── policy_change_request


The agent shouldn't directly connect to your Policy Management System.

Instead:

text
Policy Agent
      ↓
Policy Tools
      ↓
Policy Service/API
      ↓
Policy Management System


This is a major architectural improvement.

[13:14, 01/09/2026] Krishna: ### Important

Some claims operations should require *deterministic business rules* rather than LLM decisions.

For example:

text
"Is this claim eligible?"

Business Rules Engine
    → determines eligibility

Don't let the LLM make authoritative coverage/eligibility decisions.
